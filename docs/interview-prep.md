# Interview Prep & Mock Interview

## Interview Prep

Standalone interview-prep content the user authors on the dedicated `/interview-prep` page, separate from scoring config. Stored under an `interview_prep` sub-object on the same `profile`/`default` doc.

- **Fields**: `self_presentation_hr`, `self_presentation_technical`, `presenting_work_project`, `presenting_personal_project` (free text), and `qa_rubric` (managed list of `{question, answer, categories, topic}`). `categories` is a multi-select from the fixed set HR / Technical / Behavioral (server normalizes: trims, canonical casing, drops unknowns, de-dupes — `NormalizeCategories` in `MongoProfileProvider`); `topic` is a free-text grouping label (e.g. a project name; trimmed, ≤200 chars). Both are additive — old docs/history snapshots read back as `[]`/`""`.
- **Rehearsal-first rubric UI**: the page has a sticky section nav (scroll-spy, below the global nav) over sections 01 Self-presentation / 02 Question rubric / 03 Projects, and the rubric renders as a **one-open-at-a-time accordion** (`components/QaRubricAccordion.tsx`) grouped by `topic` (topic-less → trailing "General" group, case-insensitive grouping) with category filter chips (a question tagged HR+Technical shows under both). Expanded answers are read-only (`dir="auto"`) with a per-question Edit mode; "Done" only exits editing — persistence stays with the section Save row, and reorder (within group siblings) is disabled while filtered. Mock-interview debrief rewrites adopted via `POST /api/mock-interview/adopt-rubric` are auto-tagged with the session persona (HR/Technical).
- **Endpoints**: `GET/PUT /api/match/interview-prep` plus `GET /api/match/interview-prep/history/{field}` and `POST .../history/{field}/restore`, reusing the profile version-history machinery. Writes use a partial `$set`, so the scoring fields are never touched.
- The self-presentations feed the "why work here?" generation as trusted context.
- **Keyword cues (rehearsal mode)**: each self-presentation field has a Full text ⇄ Keywords toggle. Keywords mode shows an ordered list of short cue lines (Claude distills the prose via `ClaudeClient.GeneratePresentationCuesAsync` / `PromptSeeds.PresentationCues`, JSON `{cues:[…]}`) so the user speaks from memory instead of reading verbatim. Cues are **cached per saved version**: stored on the `interview_prep` doc as `self_presentation_hr_cues` / `self_presentation_technical_cues`, generated on first view and served without a Claude call thereafter. `POST /api/match/interview-prep/cues` takes `{field, force}`, reads the *saved* text server-side, and short-circuits when a cached set exists (`force` regenerates). Saving changed text drops that field's cues (`CarryCues` in `UpsertInterviewPrepAsync` carries them forward only when the text is unchanged); the next view regenerates. The cue lines render `dir="rtl"` (RTL list items) for clean mixed Hebrew/English bidi.

## Mock Interview

Interactive, turn-by-turn AI interview practice on the dedicated `/mock-interview` page (linked from the nav, from `/interview-prep`, and — bound to a specific role — from the tracker application detail page via `?applicationId=&company=&jobTitle=`).

- **Flow**: the user picks a persona (HR or technical), language (Hebrew default), and question count (4–10). Claude plays the interviewer, asking one question per turn, weaving live follow-ups around the user's answers, and giving a one-line `nudge` on each answer. "End & debrief" (or hitting the question target) produces a scored summary.
- **Stateless turn engine**: the client holds the full transcript and posts it each turn to `POST /api/mock-interview/turn` → `{nudge, nextQuestion, isFollowUp, done}`. No server-side session state during the interview.
- **Models**: per-turn questions use **Haiku** (fast/cheap, high-frequency); the end-of-session debrief uses **Sonnet**. Both live in `ClaudeClient` (`GenerateMockInterviewTurnAsync` / `GenerateMockInterviewDebriefAsync`, prompts `PromptSeeds.MockInterviewTurn` / `MockInterviewDebrief`). Both calls are **non-streaming** and **uncached**: prompt caching was evaluated and doesn't engage for the **Haiku** model at this prompt size — the SDK's `AutomaticToolsAndSystem` heuristic + explicit `cache_control` both no-op for Haiku, while Sonnet caches the identical ~4K-token prompt (verified against live token-usage). So the turns run uncached (Haiku is cheap anyway); don't re-attempt it. Only the **scoring Evaluator** (streamed Sonnet) uses prompt caching.
- **Trusted vs untrusted**: the system prompt carries trusted context (profile, the persona-matched self-presentation, project pitches, and the `qa_rubric` questions as a skeleton); the user message XML-wraps untrusted data (candidate answers in `<candidate>`, transcript in `<transcript>`, job/company context in `<job_context>` when bound) so injected instructions are ignored.
- **Debrief**: `POST /api/mock-interview/debrief` scores the transcript on a fixed 1–5 rubric (Structure / Relevance / Specificity / Clarity) and returns `highlights`, `improvements`, and `rewrites` (`{question, suggestedAnswer}`).
- **Persistence**: completed sessions are saved to the `mockInterviewSessions` collection (`IMockInterviewRepository`) and listed/reopened from the setup screen (`GET /api/mock-interview/sessions`, `GET .../sessions/{id}`).
- **Closed loop**: a debrief rewrite can be adopted into the interview-prep Q&A rubric via `POST /api/mock-interview/adopt-rubric`, which appends through `UpsertInterviewPrepAsync` (history-snapshotted, undoable; scoring fields untouched).
- **Rate limiting**: the `/turn` and `/debrief` endpoints use a dedicated `mock` fixed-window limiter (40 req/min — higher than `match`'s 10, since each session is many turns), with transcript caps (80 turns, 20K chars/turn).
- **Voice input**: the answer composer has a push-to-talk mic (`client/src/components/MicButton.tsx`, browser Web Speech API — Chrome/Edge only). Shared component (`variant: 'editorial' | 'neutral'` picks `--ed-*` vs. plain shadcn token styling depending on whether the caller is inside `.editorial` or a portal-rendered dialog); also used by the Interview Insights retro modal.

## Interview Insights

A pure observation feed over *real* interviews tracked in the Applications tab — **deliberately decoupled from the interview-prep Q&A rubric** (no adopt-into-rubric action). It was designed as a mock-interview-style closed loop (retro → rubric entry → rehearsal) first, then decoupled: the rubric's own UX wasn't intuitive enough yet to justify forcing insights into a question/answer shape. Revisit coupling them once that changes.

- **Structured retro capture**: `Interview` (`server/api/src/Core/Models/Interview.cs`) carries `RetroRating` (1-5, presence = "has a retro"), `RetroWentWell`, `RetroToImprove`, `RetroCategories` (same fixed HR/Technical/Behavioral set as the Q&A rubric, shared via `InterviewCategories` in `Core/Profile/IProfileProvider.cs`). These ride the existing `PUT /api/interviews/{id}` — no dedicated retro endpoint. Trigger: in the tracker's Interview edit form, ticking `Completed` false→true and saving opens a separate retro modal (`client/src/components/InterviewRetroModal.tsx`, neutral shadcn tokens — it's portal-rendered, outside `.editorial`) instead of saving immediately; Save merges the retro into the same PUT, Skip persists the completion without one. `Completed` itself is unrelated to application outcome — it just means the interview happened. Both retro textareas support voice dictation via the shared `MicButton` (see Mock Interview section below).
- **Insights page** (`/interview-insights`, in the nav's Interview group alongside Interview Prep and Practice Interview — cross-application by design, not a Tracker tab): `GET /api/interview-insights/retros` lists every retro-bearing interview across all applications, most recent first.
- **Persisted, regenerate-on-request summary** (not incremental): `InterviewInsight` (`Core/Models/InterviewInsights.cs`) is a *singleton* Mongo doc (`interviewInsights` collection, fixed id `"current"`) holding one free-form prose `Summary`, the `SourceRetroIds` it was generated from, and `GeneratedAt`. `GET /api/interview-insights` returns it plus `newRetroCount` (retros added since `SourceRetroIds`, for a staleness nudge) and `insufficientData` (fewer than 2 retros total). `POST /api/interview-insights/synthesize` (rate-limited `insights` policy) re-reads **all current raw retro text** — never the previous summary — and upserts a fresh `InterviewInsight`. Deliberately batch, not incremental: summarizing-a-summary on each new retro would compound drift over time (each hop loses grounding in what the earlier retros actually said); re-reading everything fresh each time stays accurate at the cost of a slightly larger prompt, which is cheap at realistic retro volumes. Prompt: `PromptSeeds.InterviewInsights` (asks for one coherent paragraph, not structured themes), config `ScoringConfig.InterviewInsights`.
- **Demo mode**: retro-save (`PUT /interviews/{id}`) is a normal blocked write. `POST /interview-insights/synthesize` **persists** now (unlike the old ephemeral-themes version), so it's also a normal blocked write, not allowlisted — demo visitors see whatever insight is already cached but can't trigger a fresh one. `GET /interview-insights` (reading the cached insight) is unaffected, GETs are never demo-gated.
