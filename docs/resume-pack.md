# Generate Pack — AI-tailored résumé

- Lives on the Tracker's Applications tab, **To Apply section only** (`Analyzing`/`DecidedToApply`) — not a new kanban lane. A row shows "Generate Pack" until one exists, then "Review Pack". Deliberately scoped down from a 3-column Added/Ready/Applied drag-and-drop board — no new DnD dependency, no new columns. Revisit that if the simple version proves the concept.
- **Grounding rule**: the tailored résumé may only select, reorder, and lightly rephrase what's already in the candidate's `StructuredProfile` — never invent an employer, date, title, or metric. Same rule the rest of the app's AI features already follow (`docs/scoring-and-search.md`). Stated in the `PromptSeeds.ResumePack` system prompt **and** enforced at runtime by `ResumePackValidator` — see below. A prompt rule with no code check behind it is not a rule: three defects the prompt already forbade (a computed "13+ years", a header title contradicting the summary, a side-project capability blended into employer experience) shipped into a PDF anyway.
- **v1 is résumé-only**, no cover letter — kept the generation and review surface to one document. A natural fast-follow once this pipeline is proven.
- `ResumePack` (`Core/Models/ResumePack.cs`) is keyed 1:1 by `ApplicationId` (not a singleton like `InterviewInsight`), stored in its own `resumePacks` collection, cascade-deleted with the application (`ApplicationRepository.DeleteAsync`).
- **Only the structured content is persisted — no PDF bytes in Mongo.** `GET /api/applications/{id}/pack/pdf` renders the PDF from that content on every request via QuestPDF (`Infrastructure/Pdf/QuestPdfResumeRenderer.cs`). No AI call on download, so it's cheap to re-download and the template can evolve without regenerating content. `POST /api/applications/{id}/pack` is the only step that calls Claude (`"pack"` rate limit, 10/min) and persists.
- Résumé header contact info (`FullName`/`Email`/`Phone`/`Location`) is a small addition to `StructuredProfile`, editable in a "Contact" field group at the top of the Profile page — used only for the PDF header, never sent to any prompt.
- **Validation has three tiers** (`Core/Models/ResumePackValidator.cs`), and the difference is the point. **BLOCK** — unrepairable, the pack is refused with `422` and never persisted. **REPAIR** — mechanical and unambiguous, so the server fixes the output and records what it changed (a skill item with no profile counterpart is dropped; a tier-4 "Worked in…" highlight is moved off the top of its entry). **FLAG** — recorded on the pack and logged, generation proceeds. `Validate` returns the synthesis *with repairs applied*, so the endpoint must persist that, not the raw model output.
- **Only two rules block**, both exact comparisons over unambiguous data, both with a real caught defect behind them: `FigureNotInProfile` (every numeric figure must be quoted verbatim from the profile or supplied as a derived fact) and `TitleDisagreesWithSummary` (`targetTitle` must prefix the summary's opening). Everything else flags. **Blocking is expensive and the bar is evidence, not plausibility** — see the `FLAG-TIER BY MEASUREMENT` note in the validator header before promoting anything.
- **Figures come from exactly two sources.** Quoted verbatim from the profile, or **derived** server-side by `ProfileFacts` (`Core/Profile/ProfileFacts.cs`) and injected into the prompt under `# DERIVED FACTS` for the model to quote. Currently one derived figure — `yearsOfExperience`, elapsed from the earliest employment start, taking 31 December as the start month since profile dates carry no month and any other choice overstates. Nobody should have to type their years of experience into their profile as a literal string; it goes stale the moment the year turns, and a shared demo persona would carry whatever was seeded. Matching is digit-bounded, not substring: a CV is dense with years, so `13` is a substring of `2013` and a fabricated "13 years" once passed against a profile that merely employed the candidate that year.
- **Advisory output, not résumé content**: `requirementCoverage` (one row per requirement — `requirement`/`coverage`/`gapType`/`evidence`) and `confirmationItems` are emitted **before** the résumé fields so the model classifies every requirement before writing any prose. `gapType` decides the response — `wording` means the evidence is in the profile and the writer failed to surface it (fix it in the résumé, no confirmation item), `evidence` means generate one focused question, `capability` means state it plainly and never write around it. One row per *technology*: a single label stretched over "Kafka, Redis, AWS, Docker, Kubernetes" lands pessimistic and hides what's real. Neither field is rendered into the PDF.
- **The `ResumePack` model call is Sonnet 5** (`Scoring:ResumePack` in `appsettings.json`), at `MaxTokens` 16000 — on the `-5` models the budget is shared with thinking, so 4096 no longer leaves room for the pack itself. See the `-5` model note in `AGENTS.md`: without the thinking cap this path fails outright.
- The stored `MatchAnalysis` is fed into the prompt as `<match_analysis>`. The Evaluator already scored this posting against this profile at ingest; without it the pack re-derives the same reading and can contradict the score shown beside it. It steers *emphasis* only — explicitly not a source of facts, and nothing in it may be quoted or restated as one.
- Demo mode: `POST /pack` is allowlisted despite being a persisting write — the one deliberate exception to "AI analyses stay enabled, everything else 403s," since it's the headline feature and cost is capped by the shared `"pack"` rate limit (10/min, same as production). Matched by path pattern (the `{id}` is dynamic) and POST-only, so `PUT /pack` (the no-AI manual-edit route) still 403s like every other mutation. Both GETs are plain reads, ungated.
