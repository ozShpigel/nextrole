# Scoring Pipeline & Semantic Search

**Scope (post-RAG migration): per-job scoring now serves ONLY the manual "Score a Job" page (`POST /api/match`).** Discovery no longer scores jobs — it ingests + embeds them, and matching happens on demand via vector search + a single advisor call (see **Semantic search (RAG)** below).

Each job scoring = 2 Claude API calls: Analyst (Haiku) + Evaluator (Sonnet with extended thinking). The **Analyst is a generic job-description parser** (raw posting → `ParsedJob` JSON; `PromptBuilder.BuildAnalysisPrompt` passes the posting in the user message inside `<job_description>`). The **Evaluator** scores fit. Both prompts are written to be **generic and objective** — no candidate/role/stack is baked in; the candidate-specific signal comes only from the injected profile.

## The professional profile (user-editable INPUT)

- **The professional profile is a user-editable INPUT** (not configuration). It is **structured**: experience & skills are LLM-normalized from pasted free text (`POST /api/match/profile/normalize` → `PromptSeeds.NormalizeProfile` → `NormalizedProfile`), while **strengths** and **core values** are explicit manual inputs (never auto-extracted). Stored as `StructuredProfile` on the `profile` doc; `ProfileRenderer.Render` produces the canonical `<professional_profile>` string saved as `content` and injected into prompts via `{{USER_PROFILE}}` — so all consumers (`GetProfileAsync`) keep receiving a plain string. Edited on the Settings page; version-history field is `profile`. Seeded from a **fictional** sample persona (`server/api/Data/sample-profile.json`). **Never hand-edit `content` — edit the structured fields.** Keep agent prompts generic/objective (no candidate/role/stack baked in); candidate-specific signal comes only from the injected profile.
- **Résumé upload**: the same normalize result can also be produced from an uploaded résumé via `POST /api/match/profile/normalize-file` (`IFormFile`, `.DisableAntiforgery()`, same `match` rate limit). **PDF** is handed to Claude as a native `DocumentContent` base64 block (no extraction lib); **TXT** reuses the free-text path; other types → 400. Both share `ClaudeClient.NormalizeProfileCoreAsync` (system prompt + `ExtractJson` + deserialize) with the text path and return the same `NormalizedProfile`. Client: `useNormalizeProfileFile` + the "Upload résumé" control on Settings; `matchApi` skips the JSON `Content-Type` when the body is `FormData`. Demo-allowlisted in `Program.cs` (non-persisting AI). The merge preserves manual strengths/core values, exactly like paste→Normalize.
- **Skills / Strengths / Core values UI**: edited as **chip inputs** (`components/ChipInput.tsx`) — type-to-add (Enter/comma/blur/+Add), removable chips, case-insensitive dedupe, plus curated `suggestions` quick-add. Skills are five category chip groups; strengths/core values are flat lists. The underlying data stays plain `string[]` arrays.

## Read-only configuration (Options pattern)

- **Scoring config & prompts are read-only configuration** (admin-only), bound via the .NET Options pattern — not user-editable data. `scoring_config` (models, temperature, max tokens, thinking, `min_score_to_save`, verdict bands) lives in `appsettings.json` under `Scoring`, bound to `ScoringConfig` via `IOptions<ScoringConfig>`. The Analyst/Evaluator system prompts default from `PromptSeeds.cs`, bound via `IOptions<PromptOptions>`. Both override per-deploy with env vars (`Scoring__Evaluator__Temperature`, `Scoring__MinScoreToSave`, `Prompts__Analyzer`, `Prompts__Evaluator`, …). Changing either is a redeploy/restart — there is **no** runtime UI/endpoint to edit them and no 30s hot-reload.

## Dimensions, verdicts, mechanics

- **Scoring dimensions**: Technical Fit (35pts), Engineering Execution Fit (30pts), Sustainability & Pace Fit (35pts)
- **Sub-component breakdown**: each dimension's `breakdown.<dim>.components[]` array (modeled by `ScoreComponent` in `MatchResponse.cs`) splits its score into sub-criteria, each with `name`, `score`, `maxScore`, and a one-sentence `reason` — Technical Fit → Core Stack (0-20) + System Design (0-15); Engineering Execution → Development Practices/Role Clarity & Ownership + Engineering Maturity; Sustainability & Pace → Work-Life + Communication/Pace + Growth/Long-term Risk. Dimension score = sum of its components; surfaced in the discovery UI via the "Score Breakdown" button on each job card, alongside a "Signals" summary (recommendation green/red flags). A component may also carry a `reviewAdjustment {base, delta}` (see Employee-review scoring below), rendered in the breakdown as `base N ±delta from employee reviews`.
- **Role-level match rule (System Design cap)**: the Evaluator caps **System Design** at the "transferable concepts" band (4-7 of 15) when the role demands a level the profile never demonstrates — Architect / Staff / Principal titles, or people-management scope — and notes the gap in the component `reason` + `redFlags`. Pure seniority prefixes ("Senior") never trigger it; it targets undemonstrated *role scope*, not years. (Added because a "Senior Software Architect" scored 62 for a candidate who was never an architect.)
- **Verdicts**: STRONG_YES, YES, MAYBE, NO, STRONG_NO, INSUFFICIENT_DATA
- **Auto-save was retired with the RAG migration** — discovery no longer scores, so nothing auto-saves. Saving is always explicit (Search results / Run detail / manual page). `min_score_to_save` still drives `shouldApply` on the manual path.
- **JSON resilience**: `ClaudeClient.cs` has lenient deserializers, fence/brace extraction, comment stripping, and auto-retry with "return ONLY JSON" nudge
- **Evaluator request**: streamed (keeps the connection alive on long generations), `max_tokens` 8192 (4096 truncated large verdict JSON → MATCH_FAILED), with prompt caching on the static system prompt (`PromptCacheType.AutomaticToolsAndSystem`)
- **Analyst `max_tokens`**: 4096 (`Scoring:Analyst:MaxTokens`). 2048 truncated the `ParsedJob` JSON on long postings → the parse retry (a "return ONLY JSON" nudge) can't fix a length truncation → `/api/match` 500. Bumping it removed that failure (and the wasteful double-call retry).

## Semantic search (RAG)

Discovery is **ingest-only**; matching is **on-demand** via MongoDB Atlas Vector Search + ONE Claude call. This replaced per-job scoring in discovery (2 Claude calls × every scraped job) and the entire batch/cron Evaluator path — both were deleted, not left dormant.

- **Ingest** (`orchestrator.py` `run_discovery`, statuses `pending → scraping → embedding → completed`): scrape (jobspy now keeps `job_level` + `is_remote`) → title triage (unchanged) → embed relevant jobs with OpenAI `text-embedding-3-small` (1536 dims; `embeddings.py`, batched 100/request; a failed chunk stores jobs without `job_embedding` → invisible to search, counted in `jobs_embed_failed` and surfaced on the Run detail page as a collapsed "Not embedded (N)" fold — gated on that counter so pre-RAG historic runs don't show it) → insert `DiscoveredJob` docs. `GET /runs/{id}/jobs` excludes the raw vector (~12KB/doc) and sends an `embedded` boolean instead. The duplicate check remains as a flag only. Cron entrypoints: `python -m app.cli run-all` (every `is_active` criteria, sequential — the Render Cron Job command, daily `0 5 * * *`) or `run <criteria_id>` (one); both ensure the TTL index (`app/indexes.py`, shared with the web `lifespan`) and `run-all` exits non-zero when no criteria are active so the cron visibly fails.
- **Atlas index** (manual, one-time, Atlas UI → type `vectorSearch`, name **`jobs_vector_index`** on `discovered_jobs`): `job_embedding` (1536, cosine) + filter fields `discovered_at` / `is_remote` / `job_level` / `site`. `$vectorSearch` errors until it's Active — the search endpoint maps that to 503.
- **Search** (`POST /api/search` on the scraper, `services/search.py`, client page `/search`): fetch the **HyDE search query** (see below; falls back to the raw rendered profile if the endpoint errors) → embed it (re-embedded per search; cheap) → `$vectorSearch` with in-index filters + `limit×5` overfetch → **location is a Python post-filter** (jobspy locations are free text; index filters are equality/range only) → **exclude acted-on jobs** (see below) → dedupe by `job_url`, then by normalized `(company, title, location)` (boards list the same posting under multiple URLs) → cap at `limit` (1–15) → enrich **only the top-N** companies (news+Glassdoor moved here from ingest) → `POST /api/match/advise`.
- **Acted-on exclusion** (`search._excluded_urls`): search results hide jobs the user already handled — discovered jobs flagged `dismissed` or `saved_to_tracker`, plus every tracker application's `JobUrl` (covers applies from any route: mailbot, manual add). Matching is **by URL set, not the hit's own flags**, because nightly re-scrapes insert fresh copies of the same posting with flags reset — dismissing one copy must hide all copies. Search result cards have a Dismiss button (reuses `POST /api/discovery/jobs/{id}/dismiss`), so runs stay fresh: each run fills with the best *unhandled* jobs. Deliberately **not** applied in `recall_eval.py` — its ground truth IS applied jobs.
- **Advisor** (the one Claude call, `ClaudeClient.AdviseAsync`, `PromptSeeds.Advisor`, `ScoringConfig.Advisor` = Sonnet/8192): profile loaded server-side via `IProfileProvider` (scraper never sends it); postings are untrusted, XML-wrapped in `<job_postings>`, descriptions capped at 8K chars each. Returns `AdvisorResponse` — Hebrew second-person `overallRecommendation` + `rankings[{jobId, rank, verdict apply|maybe|skip, rationale, greenFlags, redFlags}]`. `similarity` is passed as a weak prior the model may override. Results are **ephemeral** (not persisted); Save-to-tracker reuses `/api/discovery/jobs/{id}/save`.
- **Retention (M0 512MB)**: TTL index `ttl_discovered_at_45d` on `discovered_at`, ensured at scraper startup. Tracker-saved jobs are full copies in the tracker DB, so the purge is safe. ~18–20KB/doc (12KB of that is the embedding).
- **Demo mode**: `/api/match/advise` is in the API `analysisAllowlist`; `/api/search` is in the scraper's `DEMO_ANALYSIS_ALLOWLIST` (both non-persisting analysis).
- **`job_level` caveat**: populated by LinkedIn only — filtering by seniority excludes jobs from other boards (null `job_level`); the UI copy says so.
- **Criteria ≠ search filters** (two decoupled filter sets): saved `SearchCriteria` (titles/locations/`hours_old`…) are **scrape** parameters — they decide what enters the pool; the Search-page filters (limit/days-back/location/remote/seniority) are **query-time** `$vectorSearch` parameters. "Collected within (days)" (`days_back`, default 3) filters on `discovered_at` — the scrape date, not the board's posting date (`date_posted` is an unreliable free-text string). A search spans **all** criteria and runs within its date window, and vector similarity against the *profile* — not the criteria — decides what surfaces. The criteria's title doubles as the triage search-intent, so a vague title hurts triage quality too.
- **`SearchCriteria.min_score_to_save` is vestigial**: it drove the retired auto-save; discovery no longer reads it. The API-side `Scoring.MinScoreToSave` still drives `shouldApply` on the manual path only. **Removed from the client UI** (criteria card meter + form field); still defaulted in the scraper schema/model — a future cleanup can drop it there too.
- **LinkedIn politeness guardrails** (scraping is unauthenticated — blocks are per-IP 429s/soft blocks, not account bans, and jobspy swallows them silently): (1) **pacing** — random 8–20s sleep between each title×location search (`scraper.PACING_SECONDS`) + 30–60s between criteria in `run-all`; (2) **search budget** — titles × max(1, locations) ≤ `MAX_SEARCHES_PER_RUN` (12), enforced in `CreateCriteriaRequest` (422) and merged-state checked on partial PUT (400), mirrored as a live counter + submit block in `CriteriaPanel.tsx`; (3) **throttle visibility** — runs carry `searches_total/failed/empty`; the runs timeline warns "N of M searches returned nothing — possibly rate-limited" when any search failed or all came back empty. Pytest: `tests/test_criteria_schema.py`. The discovery page also groups run history by day (2 newest days visible, older fold into "Earlier") and links to the Search page (matching happens there, not in discovery).
- **HyDE multi-facet search queries** (`GET /api/match/profile/search-query`): the `$vectorSearch` query is not the raw profile but the profile **rewritten as 1-3 ideal job postings, one per distinct role facet** (`PromptSeeds.IdealPostings`, `ClaudeClient.GenerateIdealPostingsAsync`, one-shot Sonnet, JSON `{facets:[{name, posting}]}`). Two rationales: (1) *genre gap* — a résumé and a posting are different text genres, so raw-profile↔posting cosine partly measures genre distance; posting-vs-posting closes it (posting shape mirrors `build_job_embedding_text`); (2) *centroid problem* — one query vector averages a multi-faceted profile, under-serving secondary facets; per-facet queries fix that. The scraper embeds each facet (one batched OpenAI call), runs **one `$vectorSearch` per facet**, and merges with **Reciprocal Rank Fusion** (`search.fuse_rankings`, k=60; hits carry `facet_ranks` + best-facet `similarity`; pytest: `tests/test_search.py`). **Cached** on the profile doc (`search_query.facets`) keyed to the profile's `updated_at` — regenerated once per profile edit or with `?force=true`; a cache hit costs no Claude call. The scraper's `get_search_queries` **fails open** to the raw profile as a single facet so search degrades rather than breaks. Rate-limited (`match`). Being a GET, this endpoint doesn't pass through the demo write-block middleware (which only inspects POST/PUT/PATCH/DELETE) — so it's made demo-safe internally instead: in `DemoMode`, `?force=true` is ignored and a cache-miss generation is never persisted, bounding a demo visitor to at most one Claude call per request with no write to the seeded data. **Facet focus**: `POST /api/search` accepts an optional `facet` (a facet name) to run ONE facet's vector with no fusion (`search.select_facet`; unknown name → 400 listing the options). The Search page shows the cached facet names as "Search focus" chips (default "All roles" = fused, `useSearchFacets` query; chips hidden when 0-1 facets) and each result card shows its per-facet `facet_ranks` badges, so the fused order is inspectable.
- **Retrieval recall eval (golden set)**: `python -m app.cli eval-recall` (scraper venv) measures the silent-miss risk of the retrieval stage. Ground truth = every tracker application with a `JobUrl` (jobs actually pursued); the eval embeds the current profile via the production path, runs one unfiltered `$vectorSearch` over the whole pool (`numCandidates` 10k ≈ exhaustive), and reports each golden job's rank + Recall@15/30/50 — bucketing unmeasurable jobs (TTL'd out / never scraped / not embedded, with triage distinguished from embed failure). Needs the API up (profile fetch) + `OPENAI_API_KEY`; one embedding call, **no Claude calls**. `--tracker-db` overrides the applications DB when it differs from the scraper DB; ranks are pool-wide (real searches rank within a `days_back` window, so at-the-time ranks were likely equal or better). The report header names the query source + facet names, and each ranked job shows its per-facet ranks, so retrieval configs are comparable across runs. Measurements (2026-07-13, 5 measurable of 26, pool 287, fused ranks): raw profile → ranks 3/9/54/95/96 (Recall@15 40%); single HyDE posting → 7/12/41/75/109 (mid-tail better, top-2 and the outlier worse — diagnosed as a facet problem); **multi-facet HyDE + RRF → 3/9/22/66/105 (Recall@30 40%→60%, median 54→22)** — dominates both prior configs on 4/5 jobs; the Red Hat outlier (#92/#111 in *both* facets) is a genuine low-similarity miss no query reformulation fixes. Logic: `app/services/recall_eval.py`; pytest: `tests/test_recall_eval.py`.
- **Cost profile (measured)**: ingest ≈ $0.006/run (triage ~½¢ + embeddings ~0.1¢; text-embedding-3-small is $0.02/M tok) vs ~$2.5-3 under the old per-job scoring. A search ≈ $0.10-0.15, dominated by the N job descriptions in the advisor input — lowering `limit` scales it near-linearly.
- **Atlas index console nuance**: "Documents (Estimated)" counts *scanned* docs (the whole collection, and it's a Lucene estimate that can read high right after a build), not vectors — only docs with `job_embedding` contribute (~6KB each in index size).
- **Abort / `cancelled`**: stopping a run (`POST /api/discovery/runs/{id}/abort`) sets the terminal status **`cancelled`** (not `failed`). FastAPI can't cancel the in-flight `BackgroundTask`, so every orchestrator status write is guarded with `{"status": {"$ne": "cancelled"}}` — the still-running task can't resurrect a cancelled run. Frontend renders `cancelled` as neutral grey (`statusClass` → `status-dim`) in `lib/discovery.ts`.

## Manual scoring (paste & score)

The `/score` page (`ManualScorePage.tsx`, nav: "Score a Job") lets the user paste a job description and score it on demand — no discovery run needed. It reuses the existing live path with **no new backend**: `useScoreJob` POSTs `{jobDescription, title?, company?, location?}` to `POST /api/match` and renders the `MatchResponse` with the shared `AnalysisCard`. Title/company are optional inputs (the analyst extracts them when blank). "Save to Tracker" mirrors the scraper's `save_to_tracker` payload — `POST /api/applications` with `status: "DecidedToApply"`, `source: "manual"`, `matchAnalysis` = the response JSON minus the snapshot fields (snapshots go in their own Application columns) — then links to the new tracker entry. No company-news/Glassdoor enrichment on this path.

## Employee-review scoring (server-enforced caps)

Deep Glassdoor sub-ratings (see Company Enrichment) feed Engineering Execution & Sustainability sub-scores — but **the prompt's numeric caps are not trusted; the server re-derives them**. Key lesson (recorded in memory): LLMs do **not** reliably obey prompt-stated numeric caps under strong negative evidence, and a "score the base, then adjust" procedure gets gamed by deflating the base. So each eligible component returns a structured `reviewAdjustment {base, delta}` and `JobMatchService.Correct` → `EnforceReviewCaps` **clamps `delta`** by evidence volume (±1 if reviewCount <50/missing, ±2 for 50-199, ±3 for ≥200), zeroes adjustments on non-eligible components (`ReviewEligibleComponents` = Engineering Maturity & Stability / Pace & Workload / Long-term Risk), then **rebuilds dimension sums + overallScore before the verdict-band correction**. Missing review data never penalizes. Prompt→component mapping and direction thresholds live in `PromptSeeds.Evaluator` (EMPLOYEE REVIEW EVIDENCE section). Residual caveat: base contamination can still ~2× the intended impact in the worst case (inherent to single-call scoring); the airtight fix would be deterministic code-computed deltas.

## AI title triage (pre-embedding filter)

Job boards pad niche searches with off-target titles (a "DevEx" search scrapes "DevOps Engineer", "Data Engineer", …). Before any embedding, the orchestrator runs **one Haiku call per run** to drop clearly off-target titles: `match_client.triage_titles(settings, search_intent, jobs)` → `POST /api/match/title-triage` (`ClaudeClient.TriageTitlesAsync`, `PromptSeeds.TitleTriage`, JSON `{results:[{index, relevant, reason}]}`). It is **lean-permissive** (keeps borderline/semantic matches like "Infrastructure Engineer (Developer Tooling)") and **fails open** — any failure keeps every job (`triage_titles` returns `None`; callers keep all). **People-management titles are their own role family**: "Team Leader"/"Engineering Manager"/"Head of"/Director/VP are off-target unless the search intent itself includes management titles (scope, not domain — "DevOps Team Leader" is filtered for an IC intent), while IC-plus titles (Tech Lead, Lead Engineer, **Team Lead** — the -er suffix is the line, and Haiku needed a worked-example pair in the prompt to hold it, abstract prose wasn't enough) always stay. **Language parity**: titles in any language (Hebrew common) are translated and judged by the same rules — an unfamiliar language is never "uncertain → keep" (a Hebrew mechanical-design title was slipping through while its English twin was filtered). Scraped titles are **untrusted data** (XML-wrapped `<scraped_titles>`, intent in `<search_intent>`). Dropped jobs persist as `DiscoveredJob(triaged_out=True, triage_reason=…)` — never embedded — and the run carries `jobs_triaged_out`; the Run detail page hides them from the list and shows a collapsed "Filtered by title triage (N)" `<details>`. Endpoint is scraper-internal (no rate limit, max 200 titles) and demo-allowlisted in `Program.cs`.

## Company Enrichment

The Scraper enriches jobs with external data **at search time, for the top-N vector-search hits only** (moved off the ingest path with the RAG migration — enrichment used to run for every scraped job). The payloads feed the search **advisor** call; the manual `/api/match` path takes them as optional request fields:

- **Company News** — Google News RSS headlines (`news_client.py`). Passed to the evaluator prompt in `<company_news>` XML tags. AI reports green/red signals in `companyNewsAnalysis` (does not change numeric score).
- **Glassdoor Rating** — scraped from DuckDuckGo search snippets (`glassdoor_client.py`). Passed in `<glassdoor_rating>` XML tags (a `{rating, reviewCount, url}` projection, emitted only when an overall rating exists). AI factors it into the cultural fit narrative.
- **Employee reviews (deep Glassdoor)** — the same `glassdoor_client.py` runs a **3-query DDG cascade** and parses structured review aggregates out of the snippets: per-category **sub-ratings** (`workLifeBalance` / `cultureAndValues` / `careerOpportunities` / `seniorManagement` / `compensationAndBenefits`), **recommend-to-friend %**, review count, and up to 2 verbatim snippets. Merged into the same `glassdoorData` payload (no new field — flows through every hop untouched). Q1 (`{company} glassdoor work life balance reviews`) parses the deep fields and **strips sub-rating spans before the overall-rating regex** so a sub-rating isn't misread as the overall; Q2/Q3 backfill the overall rating only if still missing. Politeness: a module-level `asyncio.Semaphore(4)` + jitter around the HTTP call. Small companies return nothing → graceful degradation (the whole payload may be `None`). Emitted to the evaluator in a separate `<employee_reviews>` block; **unlike news/overall-rating, this evidence moves the numeric sub-scores** (see Employee-review scoring above). AI green/red signals in `employeeReviewsAnalysis`. Pytest: `server/scraper/tests/test_glassdoor_client.py` (regex-parsing is the regression-prone part; DDG bolds query terms, so `_clean_text` collapses whitespace).
- **Company Summary** — on-demand AI-generated Hebrew summary (3-4 lines) of what the company does, including approximate employee count. Generated via `POST /api/applications/{id}/company-summary` using Claude's knowledge base (no external data). Persisted on the `Application` document.

Both news and Glassdoor are prefetched in parallel per search, cached per company within that search. If either fetch fails, the advisor call proceeds without it.

## On-demand AI (application detail)

Generated per-application from the tracker detail page and persisted on the `Application` document:

- **Company Summary** — see above (`POST /api/applications/{id}/company-summary`).
- **"Why work here?" answer** — a personalized single Hebrew paragraph answering the interview question. Combines the user's profile + interview-prep self-presentation (trusted, in the system prompt) with the job/company context — description, company summary, news, Glassdoor (untrusted, XML-wrapped in the user message). Generated via `POST /api/applications/{id}/why-work-here` (`ClaudeClient.GenerateWhyWorkHereAsync`, one-shot Sonnet), stored in the `WhyWorkHere` field.
