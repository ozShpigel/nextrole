# Single-tenant design, Demo mode & ApiKey gate

**Single-tenant by design** (one user, no auth — intentional). Public exposure runs **two instances of the same code**, each pointed at its own Mongo: a private real instance and a public **demo** instance on a separate seeded DB.

- The demo sets `DemoMode=true` (API) / `DEMO_MODE=true` (scraper) → tracker writes return 403 while AI analyses stay enabled (**allowlist middleware** in `Program.cs` / `main.py` — new mutating endpoints must be allowlisted to work in demo); the client reads `GET /api/config` for the read-only banner. This cuts the other way too: `POST /api/match/profile/normalize-file` was allowlisted while it only returned ephemeral parsed data, then **removed** from the allowlist once it started also persisting the uploaded résumé itself (`Core/Models/ResumeFile.cs`, shown on the Profile page's "Resume" section) — an endpoint's allowlist status has to track what it actually does now, not what it did when first added.
- Several *persisting* writes are deliberately allowed anyway, all bounded to the seeded pool: **Generate Pack** (`POST /api/applications/{id}/pack`, path-pattern matched, capped by the shared `"pack"` rate limit), the Matches page's **Add** (scraper `POST /api/discovery/jobs/{id}/save`, path-pattern matched; its downstream call to the API's `POST /api/applications` is gated on the `X-Source: ingest` header the scraper already attaches to every scraper→API request, so the same endpoint stays 403 for the client's "Import Job" feature — arbitrary URL scraping / uncapped Claude scoring has no such bound), **Dismiss** (scraper `POST /api/discovery/jobs/{id}/dismiss`, same shape as Add), mark-message-read (`PATCH /api/messages/{id}/read`), the Active board's **Remove** (`PUT /api/applications/{id}/status`, allowed only for the `Withdrawn` transition — sniffed from the request body, since every other status transition shares this same path; also fires a best-effort `POST /api/discovery/jobs/unsave`, scraper, exact-path allowlisted, to clear the originating Matches card's `saved_to_tracker` flag — miss this one and Remove still "works" but silently leaves Matches stuck showing "Added" forever, since `useUpdateAppStatus` swallows that call's failure), and Interview Prep's **Save** (`PUT /api/match/interview-prep` — a bigger write than the others, it replaces the whole self-presentation + Q&A rubric, but self-healing since `UpsertInterviewPrepAsync` already runs unconditionally on every Seeder run).
- `MongoProfileProvider`'s 30s in-memory cache (profile + interview-prep) is per-API-process — a reseed writes straight to Mongo and doesn't invalidate it, so a running API instance can serve stale content for up to 30s after a reseed. Never an issue in practice; if you need it instant, restart the API process.
- **`DemoMode` only gates writes + the banner — *which data shows* is decided by the connection string + DB-name env vars, not the flag.**
- Seed demo data (applications, profile, discovery, interview-prep, messages; **self-healing**) with `dotnet run --project server/api/src/Seeder`, run on demand whenever demo-visitor writes need resetting. Applications matched by (Company, JobTitle) get their `Status`/`AppliedAt` force-reset to the curated seed values rather than skipped; any application *not* in the curated list (added via Matches' "Add") is deleted along with its interviews/statusUpdates/résumé pack; messages are fully deleted and reinserted (resets `isRead`); discovery jobs were already fully replaced on every run. Not yet automatic — see `DemoJobFreshnessInitializer` for the one piece (discovery job timestamps) that already runs on every API startup.
- Deployment/ops for the public demo (separate DB, least-privilege Atlas user, exact env vars) live in `docs/hosting-a-public-demo.md`; `.env.example` files are kept demo-free.
- Optional integrations degrade gracefully (no Gmail → mailbot skips; app runs on just Mongo + AI key). See README.

## ApiKey gate (hosting the private instance publicly)

Needed for a cloud mailbot cron: set `ApiKey` on the API → every request must send a matching `X-Api-Key` header or 401 (constant-time compare; `/health` + `/api/config` + OPTIONS stay open; middleware in `Program.cs`); the mailbot sends it via `Tracker__ApiKey`. **Never set `ApiKey` on the demo.**

## Mailbot demo guard

The mailbot **fails fast** (exit 1) when its tracker reports `demoMode: true` at `GET /api/config` — a demo can't accept its writes, so a run against it is always a misconfiguration (this bit us: the Render cron silently synced the 6 seeded demo apps for months).
